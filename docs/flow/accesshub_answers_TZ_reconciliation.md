# AccessHub — ответы на вопросы программиста по сверке ТЗ и реализации

Дата: **2025-12-23**  
Основание: документ «Сверка ТЗ (v3) с текущей реализацией — вопросы для согласования» (`TZ_reconciliation.md`).

Цель: дать **чёткие ответы/решения для разработки** и указать, где нужно **согласование с заказчиком** (потому что это меняет формулировки/поведение относительно ТЗ).

## 1) Критические расхождения — решения

### 1.1. Выдача аккаунтов: API vs Bot Action

**Текущее в системе:** выдача идёт через API `POST /api/webapp/api/issue` (JSON).  
**В ТЗ:** описан вариант через bot action `tg.sendData()` + ответ в чат code-block.

**Решение для разработки (фиксируем):**
- ✅ **API остаётся основным и единственным рабочим путём выдачи** (транзакционность, валидаторы, логирование).
- ✅ Bot action оставляем **только как fallback/совместимость**, без использования в UI по умолчанию.

**Что требуется от документации:**
- 🔶 Обновить ТЗ: описать выдачу через API как основной путь; bot action пометить как fallback (не обязательный для UI).

**Техническое требование:**
- API обязано возвращать минимум: `receipt(order_id, game, platform, qty)` и `items[]` с `game_login/game_password` (без email).

---

### 1.2. История: пагинация limit vs page/per_page

**Текущее:** `page` + `per_page`, ответ `{items, page, per_page, total}`.  
**В ТЗ:** `limit`.

**Решение для разработки (фиксируем):**
- ✅ **Оставляем page-based pagination** (`page`, `per_page`), потому что это стандартно и удобно для UI.

**Что требуется от документации:**
- 🔶 Обновить ТЗ: заменить `limit` на `page/per_page` и привести пример ответа.

---

### 1.3. История: что видит оператор (account_id)

**Текущее:** оператор видит `account_id` в истории.  
**В ТЗ:** “оператор видит только игровые данные”, но не уточнено, считается ли `account_id` скрытым.

**Решение для разработки (фиксируем):**
- ✅ **Оставляем `account_id` в истории оператора**, так как:
	- это **не чувствительные данные** (не логин/пароль/почта),
	- помогает связывать выдачу с внутренними действиями админа/логами.

**Что требуется от документации:**
- 🔶 В ТЗ дописать: “оператор видит технический `account_id` (без email/скрытых полей)”.

## 2) Расхождения “добавлено сверх ТЗ” — что делаем сейчас

> По установке: **добавочное потом**, сейчас фиксируем только то, что **однозначно из ТЗ**.

### 2.1. Вкладка “Админ: Статистика” (добавочное)
- Это **не требование ТЗ**.
- ✅ Оставляем как есть в реализации (не мешает),
- 🔶 **в финальное ТЗ пока не включаем** (если заказчик отдельно не попросит).

### 2.2. Вкладка “Админ: Импорт” (UI поверх API)
- В ТЗ есть импорт как функциональность, но не обязательно как вкладка UI.
- ✅ Оставляем как есть (удобно),
- 🔶 в финальное ТЗ не включаем как обязательное, пока не согласовано.

### 2.3. “Админ: Аккаунты/Поиск” (структура вкладок)
- В ТЗ есть админские действия (поиск, enable/disable/reset), но структура вкладок может отличаться.
- ✅ Оставляем текущую структуру: `admin_find` (поиск + действия) + API `POST /admin/accounts` для добавления.
- 🔶 В ТЗ можно не фиксировать вкладки, а фиксировать **возможности**.

## 3) Пункты ТЗ, которые отсутствуют в реализации и должны быть сделаны

### 3.1. Импорт файлом (TXT/CSV/XLSX) — ОБЯЗАТЕЛЬНО по ТЗ
**Статус:** ❌ endpoint отсутствует.  
**Решение:** ✅ реализовать `POST /webapp/api/admin/import/file` (поддержка `txt/csv/xlsx`).

Примечание: план работ по импорту файлами оформлен отдельным документом.

---

### 3.2. Вкладка “Настройки” — заглушка (есть в ТЗ)
**ТЗ:** “Настройки (заглушка)”.  
**Реализация:** вкладки нет.

**Решение:** ✅ добавить статичную вкладку/экран “Настройки” (без функционала), текст: “будет добавлено позже”.

## 4) Неясности/решения по API деталям (для программиста)

### 4.1. URL-префикс `/api/webapp/api/...` vs `/webapp/api/...`
**Текущее:** `/api/webapp/api/...`  
**ТЗ:** `/webapp/api/...`

**Решение:** ✅ **оставить как в реализации** (`/api/webapp/api/...`), это нормальная Laravel-конвенция.  
**Действие:** 🔶 обновить примеры в ТЗ (это не меняет бизнес-логику).

---

### 4.2. Формат ответа Issue через API: JSON vs text block
**Текущее:** JSON  
**В ТЗ:** текстовый code-block (в чате)

**Решение:** ✅ JSON — основной формат (структурированный).  
**UI/WebApp** сам форматирует данные для отображения.  
**Действие:** 🔶 обновить ТЗ.

---

**Реализация:** фильтры есть.

**Решение:** ✅ фильтры оставить (это полезно и не нарушает ТЗ).  
**Действие:** при обновлении ТЗ — задокументировать фильтры (не критично для сдачи).

### 4.4. Force cooldown (admin/accounts/{id}/cooldown)
**ТЗ:** reset есть, cooldown не описан.  
**Реализация:** cooldown есть.

**Решение:** ✅ оставить (полезно админу), **но не считать обязательным по ТЗ**.  
**Действие:** при желании — добавить в расширенное ТЗ позже.

---

### 4.5. Локализация (ru/uk/en) + /lang
**ТЗ:** не требует.  
**Реализация:** есть.

**Решение:** ✅ оставить как есть (не мешает), **не включать в обязательную часть ТЗ**.

## 5) Что нужно согласовать с заказчиком (минимум)

Чтобы финализировать ТЗ без подвисаний, заказчику достаточно подтвердить 3 пункта:

1) **Выдача через API** как основной путь (bot action — fallback).  
2) **Пагинация истории**: `page/per_page` вместо `limit`.  
3) **account_id виден оператору** в истории (как техническое поле).

Все остальные пункты либо:
- уже закрыты по ТЗ,
- либо являются расширениями и могут быть вынесены “потом”.
