## 1. Критические противоречия (требуют немедленного решения)

### 1.1. Выдача аккаунтов: API vs Bot Action

**ТЗ (раздел 5, строка 144):**
> Выдача (submit=bot, action=issue): order_id, game, platform, qty  
> Данные отправляются боту через `tg.sendData()`, бот отвечает в чат code-block

**Текущая реализация:**
- Вкладка "Выдача" использует `submit.type='api'`
- Endpoint: `POST /api/webapp/api/issue`
- Ответ приходит в WebApp в формате JSON:
  ```json
  {
    "ok": true,
    "data": {
      "receipt": {...},
      "items": [
        {"game_login": "...", "game_password": "...", "account_id": 123}
      ]
    }
  }
  ```
- Fallback на bot action оставлен в schema, но не используется UI

**Вопросы для согласования:**
1. ✅ **Оставить API как основной путь?** (рекомендуется — лучше для транзакций, логирования, валидации)
2. ❌ Вернуть bot action как основной путь?
3. ❓ Оставить оба варианта с переключателем?

**Рекомендация:** Зафиксировать API как основной путь, bot action оставить как fallback для совместимости.

---

### 1.2. История: параметры пагинации

**ТЗ (раздел 6.2, строка 123):**
> `GET /webapp/api/history?limit=50&order_id=...`

**Текущая реализация:**
- Используется page-based pagination: `page=1&per_page=20`
- Endpoint: `GET /api/webapp/api/history?page=1&per_page=20&order_id=...`
- Ответ включает: `{items: [...], page: 1, per_page: 20, total: 45}`

**Вопросы для согласования:**
1. ✅ **Оставить page-based pagination?** (рекомендуется — лучше для infinite scroll в UI)
2. ❌ Перейти на limit-based?
3. ❓ Поддерживать оба варианта?

**Рекомендация:** Оставить page-based, обновить ТЗ.

### 1.3. История: что видит оператор

**ТЗ (раздел 2.1, строка 17):**
> Оператор: "В чате получает **только игровые** данные: `game_login` / `game_password`"  
> "Не видит почту/почтовые пароли/скрытые поля"

**Текущая реализация:**
- В истории оператор видит: `id`, `issued_at`, `order_id`, `game`, `platform`, `account_id`
- `account_id` — технический идентификатор (не чувствительные данные)
- Чувствительные данные (`email_login`, `email_password`) не возвращаются

**Вопросы для согласования:**
1. ✅ **Оставить `account_id` в истории для оператора?** (рекомендуется — нужен для связи с логами)
2. ❌ Убрать `account_id` из истории оператора?
3. ❓ Что именно считается "скрытыми полями"? Только email-данные или также `account_id`?

**Рекомендация:** Оставить `account_id` (это не чувствительные данные), убрать только email-поля.

### 4.4. Авторизация: заголовки initData

**ТЗ (раздел 6.1, строки 110-113):**
> Заголовок: `X-TG-INIT-DATA: <initData>`  
> или  
> body: `initData: "..."`

**Текущая реализация:**
- Поддерживаются оба варианта
- Дополнительно: `X-Tg-Init-Data` (canonical, приоритет выше)
- Fallback: `X-TG-INIT-DATA` (legacy)
- Debug bypass: `X-Debug-Tg-UserId` (только если `ACCESSHUB_WEBAPP_DEBUG=true` и `APP_ENV=local`)

**Вопросы для согласования:**
1. ✅ **Оставить поддержку обоих заголовков?** (рекомендуется — совместимость)
2. ❓ Нужна ли документация debug bypass для разработки?

**Рекомендация:** Оставить текущую реализацию, задокументировать в ТЗ.
